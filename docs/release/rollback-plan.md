## 1. 概述

### 1.1 回滚目标

在上线或灰度期间出现严重问题时，快速、安全地回退到上一稳定版本，最小化用户影响。

### 1.2 回滚原则

- **快速响应**：5 分钟内完成紧急回滚
- **用户优先**：最小化用户影响
- **数据安全**：确保数据不丢失、不损坏
- **可追溯**：完整记录回滚过程和原因

---

## 2. 回滚触发条件

### 2.1 P0 级别（立即回滚）

| 问题 | 判断标准 | 响应时间 |
|------|----------|----------|
| 系统不可用 | 服务完全不可访问 | 立即 |
| 数据丢失 | 用户数据丢失或损坏 | 立即 |
| 安全漏洞 | 发现严重安全漏洞 | 立即 |
| 成功率 < 90% | 消息处理成功率低于 90% | 5 分钟内 |

### 2.2 P1 级别（考虑回滚）

| 问题 | 判断标准 | 响应时间 |
|------|----------|----------|
| 核心功能不可用 | 主要功能无法使用 | 30 分钟内 |
| 成功率 90%-95% | 消息处理成功率低于 95% | 30 分钟内 |
| 性能严重下降 | 响应时间 > 10s | 30 分钟内 |
| 用户投诉激增 | 投诉量 > 50/小时 | 30 分钟内 |

### 2.3 P2 级别（修复优先）

| 问题 | 判断标准 | 响应时间 |
|------|----------|----------|
| 非核心功能问题 | 次要功能异常 | 24 小时内修复 |
| 成功率 95%-98% | 消息处理成功率略低 | 24 小时内修复 |
| 性能轻微下降 | 响应时间 5-10s | 24 小时内修复 |

## 3. 回滚策略

### 3.1 快速回滚（5 分钟内）

**适用场景：** P0 级别故障

**回滚方式：** 全量回滚

**步骤：**

```bash
# 1. 立即切换流量回旧版本（100%）
kubectl set image deployment/copaw copaw=copaw:v1.0 --record

# 2. 验证流量切换
kubectl rollout status deployment/copaw

# 3. 停止新版本服务
systemctl stop copaw-v2

# 4. 启动旧版本服务（如已停止）
systemctl start copaw-v1

# 5. 验证服务健康
curl http://localhost:8000/health

# 6. 验证核心功能
python tests/smoke_test.py
```

**时间分配：**

| 步骤 | 时间 | 负责人 |
|------|------|--------|
| 决策回滚 | 1 分钟 | 总指挥 |
| 切换流量 | 2 分钟 | 运维 |
| 验证服务 | 2 分钟 | 开发 |
| **总计** | **5 分钟** | |

---

### 3.2 渐进回滚（30 分钟内）

**适用场景：** P1 级别故障

**回滚方式：** 分阶段回滚

**步骤：**

```bash
# 阶段 1：降低新版本流量（50% → 20%）
kubectl set image deployment/copaw copaw=copaw:v1.0-canary
update_gray_config --percentage 20

# 阶段 2：观察 10 分钟
# 监控指标变化

# 阶段 3：继续降低流量（20% → 5%）
update_gray_config --percentage 5

# 阶段 4：观察 10 分钟
# 监控指标变化

# 阶段 5：完全回滚（5% → 0%）
update_gray_config --percentage 0

# 阶段 6：停止新版本服务
systemctl stop copaw-v2
```

**时间分配：**

| 步骤 | 时间 | 负责人 |
|------|------|--------|
| 决策回滚 | 5 分钟 | 总指挥 |
| 降低流量（50%→20%） | 5 分钟 | 运维 |
| 观察指标 | 10 分钟 | 开发 |
| 降低流量（20%→5%） | 5 分钟 | 运维 |
| 观察指标 | 10 分钟 | 开发 |
| 完全回滚 | 5 分钟 | 运维 |
| **总计** | **40 分钟** | |

---

### 3.3 数据回滚（如需要）

**适用场景：** 数据不一致或损坏

**步骤：**

```bash
# 1. 停止所有服务
systemctl stop copaw-v2
systemctl stop copaw-v1

# 2. 恢复数据库备份
pg_restore -d copaw_db /backup/copaw_db_20260331.dump

# 3. 恢复 Redis 数据
redis-cli < /backup/redis_20260331.rdb

# 4. 验证数据完整性
python scripts/verify_data.py

# 5. 启动旧版本服务
systemctl start copaw-v1

# 6. 验证服务正常
curl http://localhost:8000/health
```

**注意：** 数据回滚会导致回滚点后的数据丢失，需谨慎评估。
